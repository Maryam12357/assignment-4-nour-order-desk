# Assignment 4 — Nour's Order Desk

## API Documentation

### 1. API Overview

Nour's Order Desk uses REST API endpoints implemented with Next.js App Router Route Handlers.

The API allows the frontend to create, retrieve, update, and delete customer orders.

**Base URL:** `http://localhost:3000`

**Data format:** JSON

**Storage:** In-memory array

### 2. Order Data Structure

Each order contains the following fields:

| Field | Type | Description |
|---|---|---|
| id | string | Unique order identifier generated by the server |
| customerName | string | Customer's name |
| phone | string | Customer's phone number |
| productName | string | Ordered product |
| quantity | number | Number of items |
| unitPrice | number | Price of one item |
| total | number | Calculated total price |
| status | string | Pending, Preparing, or Delivered |

The server calculates the total using:

`total = quantity × unitPrice`

New orders receive the default status `Pending`.

### 3. GET /api/orders

**Purpose:** Retrieve all customer orders.

**Method:** GET

**Example request:**

`GET http://localhost:3000/api/orders`

**Successful response — HTTP 200 OK:**

```json
[
  {
    "id": "example-order-1",
    "customerName": "Sara",
    "phone": "70123456",
    "productName": "Vanilla Candle",
    "quantity": 2,
    "unitPrice": 12.5,
    "total": 25,
    "status": "Pending"
  }
]
```

When there are no orders, the API returns an empty array:

```json
[]
```

### 4. POST /api/orders

**Purpose:** Create a new customer order.

**Method:** POST

**Request body:**

```json
{
  "customerName": "Sara",
  "phone": "70123456",
  "productName": "Vanilla Candle",
  "quantity": 2,
  "unitPrice": 12.5
}
```

**Successful response — HTTP 201 Created:**

```json
{
  "id": "example-generated-id",
  "customerName": "Sara",
  "phone": "70123456",
  "productName": "Vanilla Candle",
  "quantity": 2,
  "unitPrice": 12.5,
  "total": 25,
  "status": "Pending"
}
```

The ID is generated by the backend. The total and initial status are also assigned by the server.

**Validation rules:**

- Customer name, phone, and product name are required nonempty strings.
- Quantity must be a positive integer.
- Unit price must be a nonnegative number with at most two decimal places.
- Invalid request bodies return HTTP 400.
- Malformed JSON returns HTTP 400.

**Example error — HTTP 400 Bad Request:**

```json
{
  "error": "Quantity must be a positive integer"
}
```

### 5. GET /api/orders/:id

**Purpose:** Retrieve one order using its ID.

**Method:** GET

**Example request:**

`GET http://localhost:3000/api/orders/example-order-1`

**Successful response — HTTP 200 OK:**

```json
{
  "id": "example-order-1",
  "customerName": "Sara",
  "phone": "70123456",
  "productName": "Vanilla Candle",
  "quantity": 2,
  "unitPrice": 12.5,
  "total": 25,
  "status": "Pending"
}
```

**Unknown ID — HTTP 404 Not Found:**

```json
{
  "error": "Order not found"
}
```

### 6. PATCH /api/orders/:id

**Purpose:** Update an existing order.

**Method:** PATCH

The API supports partial updates. Only the fields that need to change must be included.

**Example 1 — Update quantity:**

```json
{
  "quantity": 3
}
```

**Successful response — HTTP 200 OK:**

```json
{
  "id": "example-order-1",
  "customerName": "Sara",
  "phone": "70123456",
  "productName": "Vanilla Candle",
  "quantity": 3,
  "unitPrice": 12.5,
  "total": 37.5,
  "status": "Pending"
}
```

The backend recalculates the total automatically.

**Example 2 — Update status:**

```json
{
  "status": "Preparing"
}
```

Allowed status values:

- Pending
- Preparing
- Delivered

**Validation rules:**

- An empty PATCH body is rejected.
- Unknown fields are rejected.
- Invalid quantity or unit price is rejected.
- Invalid status values are rejected.
- The order ID cannot be modified.
- Failed validation must not modify the stored order.
- Unchanged fields are preserved during partial updates.
- The server recalculates the total when quantity or unit price changes.

**Invalid request — HTTP 400 Bad Request:**

```json
{
  "error": "Unknown field: id"
}
```

**Unknown order — HTTP 404 Not Found:**

```json
{
  "error": "Order not found"
}
```

### 7. DELETE /api/orders/:id

**Purpose:** Delete an existing order.

**Method:** DELETE

**Example request:**

`DELETE http://localhost:3000/api/orders/example-order-1`

**Successful response — HTTP 204 No Content:**

The server successfully deletes the order and returns HTTP 204 with an empty response body.

No JSON message is returned after successful deletion.

**Unknown order — HTTP 404 Not Found:**

```json
{
  "error": "Order not found"
}
```

The frontend asks for confirmation before sending the DELETE request.

After successful deletion, the frontend updates the displayed orders and summary information based on the successful API response.

### 8. HTTP Status Codes

| Status | Meaning | Usage |
|---|---|---|
| 200 | OK | Successful GET and PATCH |
| 201 | Created | Successful POST |
| 204 | No Content | Successful DELETE with no response body |
| 400 | Bad Request | Invalid input or malformed JSON |
| 404 | Not Found | Order ID does not exist |
| 500 | Internal Server Error | Unexpected backend error |

### 9. Frontend Integration

The frontend communicates with the API using the JavaScript `fetch()` function.

**Create Order:**

The frontend sends a POST request containing the order details. After receiving HTTP 201, it updates the displayed orders using the server response.

**Retrieve Orders:**

The frontend sends a GET request to retrieve the current orders and display them in the dashboard.

**Update Order:**

The frontend sends a PATCH request containing only the fields that need to change. After receiving HTTP 200, it displays the updated order information.

**Delete Order:**

The frontend requests confirmation before sending a DELETE request. After receiving HTTP 204, it updates the order list without attempting to parse a JSON response body.

**Error Handling:**

When the API rejects a request, the frontend displays an error message instead of assuming the operation succeeded.

The interface should reflect the actual server state rather than making unsupported assumptions about the result of a request.

### 10. Data Integrity and Business Rules

The backend is responsible for validating incoming data and protecting order information.

Important rules include:

- Order IDs are generated and controlled by the server.
- Clients cannot modify existing order IDs.
- Order totals are calculated by the server.
- Quantity must be a positive integer.
- Invalid updates must not change existing order data.
- Partial updates preserve fields that were not included in the request.
- Unknown order IDs return HTTP 404.
- Successful DELETE requests return HTTP 204 without a response body.

**Example — Invalid PATCH request:**

```json
{
  "quantity": -5
}
```

**Expected response — HTTP 400:**

```json
{
  "error": "Quantity must be a positive integer"
}
```

The existing order remains unchanged.

This behavior was verified during manual API testing using Thunder Client.

### 11. Storage Limitation

Orders are stored in memory rather than in a database.

This means orders may be lost or reset when the server process restarts.

The API is intended for a small educational CRUD application, not persistent production storage.
